# Collector privacy boundary

Only explicitly approved chat envelopes reach application content extraction and the searchable archive. Policy is checked again by the archive while writing. Names, contact lists, message IDs, chat identifiers, message bodies, captions, and raw library errors are never logged. Chat labels come from local configuration.

Initial account-wide history downloading is disabled. New approved messages are archived while connected. Defensive history-event handling also applies the chat allowlist and writes at most 100 messages per batch. This is not a promise that the server supplies complete historical coverage.

The application never sends user messages, reactions, read receipts, presence updates, or automatic replies. It prefetches eligible approved attachments through one background worker. The linked-device library still exchanges authentication, cryptographic, delivery-acknowledgment, and synchronization protocol traffic. "Read-only" refers to the application's user-message capabilities, not a network connection that transmits zero bytes.

View-once messages are skipped, including payloads already unwrapped by the library. Ordinary disappearing-message wrappers are unwrapped and approved text is retained under the local archive retention policy. Approved top-level images, video, audio, documents, and stickers can have a private attachment descriptor stored atomically with the message. Document filenames are bounded display metadata. Quote context, thumbnails, contact cards, and nested quoted attachments are not separately archived or downloaded. Absolute media URLs are not passed to the downloader. Descriptors contain private direct paths, media keys, and integrity hashes; public responses and logs must never expose them.

Prefetch uses a persistent bounded job scan and a one-slot wake signal. A single worker streams each download into the archive's private bounded temporary file with a 60-second context. The library verifies the encrypted SHA-256, HMAC, and plaintext SHA-256 and decrypts in place using small chunks. The archive rechecks current approval, message retention, descriptor identity, generation, exact length, hash, and cache quota before publishing the file. Configuration changes cancel or invalidate in-flight work. Failed jobs have bounded retries; completed cache entries follow archive eviction and retention policy. No network transfer occurs inside the message event handler.

The media-only HTTP client accepts HTTPS on port 443 under `whatsapp.net`, `whatsapp.com`, and `fbcdn.net`, including their subdomains. Redirects and environment proxies are disabled. DNS answers are checked for public destinations and the chosen address is used directly for dialing, while ordinary TLS hostname verification remains active. Unknown future CDN domains fail closed and require a reviewed update. These restrictions do not replace authentication and cryptographic integrity checks.

`session.db` is private protocol state, separate from the searchable archive. It retains linked-account identity, cryptographic sessions and keys, app-state synchronization hashes, and phone-number/linked-identity mappings needed by the library. Those protocol records can refer to peers outside the archive allowlist. The allowlist cannot prevent the linked device from receiving and decrypting other account traffic in memory.

Contact-name, chat-setting, message-secret, privacy-token, and decrypted-event stores are replaced with no-op stores, including immediately after first pairing initializes the library SQL stores. Persistent retry-message storage is disabled. These choices intentionally reduce ancillary features. The underlying schema still contains empty tables for these disabled stores. Reusing a preexisting session database from another client is unsupported; old records are not scrubbed by these wrappers.

Pairing images are generated in process memory until their QR lifetime expires. The owner process may write the current image to an owner-only ephemeral `pairing.png` in the private state directory and remove it after pairing. No pairing image is served through HTTP or MCP. Administrator-made copies have their own lifetime and must be removed after use. On Windows, POSIX file modes alone do not replace user-profile ACLs.
